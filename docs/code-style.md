# Стиль кода Project Flow Agent

Правила основаны на `docs/code-style.md` проекта Instagram Trends Search и
адаптированы для TypeScript, React и API Obsidian. Перед правкой сверяйте их
с рабочей спецификацией и [конституцией](../.specify/memory/constitution.md).
При рефакторинге сохраняйте поведение, DOM, сообщения, формат Markdown
и контракты Obsidian, если спецификация сохраняет эти контракты.

## Простота, константы и границы

- Следуйте KISS, DRY и YAGNI. Применяйте SOLID, когда код совмещает разные
  обязанности или уже есть точка расширения. Вводите хелперы, интерфейсы,
  классы и фабрики при конкретной необходимости. Классы `Plugin` и `ItemView`
  реализуют контракты Obsidian.
- Уже со второго места использования переиспользуйте общий код для одной
  операции или правила. Для одинакового ввода вычислите проверку один раз и
  используйте именованный результат. Если вводы разные, переиспользуйте
  общий предикат или условие. Сохраняйте проверки на независимых границах
  валидации и учитывайте изменение данных между проверками.
- Перед новой константой или функцией ищите существующий источник и сверяйте
  смысл. Один источник подходит для значений, которые должны меняться вместе.
  Общие константы и хелперы экспортируйте из модуля, отвечающего за этот
  контракт. Пользователи правила импортируют их из этого модуля.
- Храните статические константы в отдельных файлах рядом с кодом, который
  ими владеет. Для одного компонента используйте `constants.ts` в его папке.
  Локальные константы операции храните в её папке. Константы для всей
  кодовой базы храните в тематических сегментах `src/shared/`, например
  `lib/dom` для HTML и клавиатуры. Константы и хелперы одной страницы
  храните в её тематическом модуле.
  Для пустой строки, пробела и разделителей переиспользуйте константу с тем
  же смыслом. Именуйте служебные знаки при сборке подписей и ключей, в том
  числе в шаблонных строках.
- В скриптах сборки выносите в файл констант пути и их части (включая `.`),
  кодировки, системные коды ошибок, флаги и настройки сборщика. Давайте имена
  и значениям с одним местом использования. Сообщения об ошибках собирайте
  в именованный объект в том же файле констант.
- Ядро работает с данными. Адаптер работает с хранилищем, событиями и
  навигацией Obsidian. `ItemView` подключает React и освобождает ресурсы.
  Компоненты получают модель представления и обработчики.
- В TypeScript и JavaScript опускайте фигурные скобки у простых однострочных
  условий и стрелочных функций с одним выражением, когда сохраняются
  читаемость, поведение и возвращаемое значение. Для нескольких инструкций
  и обязательных блоков используйте фигурные скобки.
- В TypeScript и JavaScript оформляйте текстовые комментарии в формате
  `//TODO: Текст комментария.` Пишите `TODO` сразу после `//` и ставьте
  пробел после двоеточия.

## Структура исходников

- Соблюдайте Feature-Sliced Design. `src/app/` запускает плагин.
  Каждый экран находится в своём срезе `src/pages/`. Общие компоненты,
  функции и доступ к Obsidian лежат в `src/shared/`.
- Код среза распределяйте по назначению. `ui` содержит React-компоненты
  и подключение вкладки. `model` хранит типы, состояние и команды над
  Markdown. `api` связывает эти команды с хранилищем Obsidian.
- Снаружи обращайтесь к экрану через его `index.ts` и `styles.css`.
  `app` импортирует `pages` и `shared`, страницы импортируют `shared`.
  Модель страницы работает без React и Obsidian. [Слои FSD](https://fsd.how/docs/reference/layers/)

## Данные, компоненты и JSX

- Статические объекты конфигурации и текстов (`COPY`) деструктурируйте на
  уровне модуля. Извлекайте поля, которые используются по отдельности.
  Поля пропсов, параметров и модели деструктурируйте в сигнатуре или в начале
  функции. После сужения типа извлеките доступные поля в начале ветки.
  Динамические подписи оставляйте индексируемыми, а методы вызывайте с объектом,
  если им нужен его контекст.
- Размещайте компонент в собственной папке вместе с его стилями. Публичные
  экспорты компонента объявляйте в `index.ts` и импортируйте через путь к папке.
  Общий `src/styles.css` подключает стили компонентов для сборки Obsidian.
- Фиксированные строковые значения JSX-атрибутов берите из констант. Общие
  HTML-значения импортируйте из `src/shared/lib/dom`. Именуйте
  строковые константы по значению, если оно подходит нескольким атрибутам.
  Например, для строки `"true"` используйте `TRUE_STRING`.
- Имена CSS-классов оставляйте строками в `className`. При условном выборе
  классов оставляйте строки в самом выражении выбора.
- Давайте общее имя типу, который используют несколько модулей, и
  экспортируйте его через точку входа модуля-владельца. Переиспользуйте
  именованный тип доменного значения, например `TaskPeriod`, вместо
  повторяющихся обращений к строковому ключу в типах.
- Ограничивайте CSS контейнером плагина и используйте переменные темы
  Obsidian. Если используются CSS Modules,
  деструктурируйте статические классы там, где это убирает повторение, и
  оставляйте динамические модификаторы индексируемыми.
- Извлекайте вложенное значение один раз и давайте ему понятное имя.
  Если длина списка нужна в нескольких местах, вычисляйте её в начале
  компонента и используйте одну константу в условиях, JSX и колбэках.
  Вычисляйте производные значения, включая `href`, до JSX. Проверки вариантов
  состояния оформляйте именованными предикатами, например `isKindReady`,
  и переиспользуйте их в компонентах и вызывающем коде. Предикат сохраняет
  сужение типа.
- Многострочные элементы `.map()` и условные блоки выносите в именованные
  `render…`-функции перед основным `return`. Самостоятельный React-компонент
  с собственной ролью размещайте в отдельном файле. Сохраняйте DOM, ключи,
  порядок элементов, условия показа и доступные имена. Простые однострочные
  выражения оставляйте в JSX. React hooks вызывайте на верхнем уровне
  компонента или хука.
- Когда варианты используют одинаковую разметку, вычислите различающиеся
  свойства заранее и используйте один JSX-блок.
- Для выбора из конечного набора значений используйте типизированную
  таблицу, если она проще цепочки сравнений. Сохраняйте запасное поведение
  для неизвестных значений.

## Контракты, валидация и ошибки

- Переиспользуйте общие константы для идентификаторов представлений, ключей
  свойств Markdown, а при работе с внешним API — для HTTP-методов, статусов,
  заголовков, ролей модели и ключей запроса. Сообщения об ошибках одного
  модуля собирайте в именованный объект. Учитывайте назначение каждой ошибки,
  даже когда тексты совпадают.
- На границе с неизвестными данными используйте схемы Zod и штатные проверки
  TypeScript и JavaScript (`typeof`, `Array.isArray`, существующий type guard).
  Сохраняйте различие между примитивной строкой и объектом `String`, `0`
  и отсутствующим значением, пустым и пропущенным полем.
- Давайте имена числовым пределам, регулярным выражениям и настройкам
  внешних запросов, если они выражают важное или повторно используемое
  правило. При рефакторинге сохраняйте значения и принимаемые входы.
- Строки, которые управляют поведением, например ключи frontmatter, статусы
  и имена обязательных файлов, держите рядом с их контрактом. Типы, проверки
  и производные пути выводите из этого источника, когда они должны меняться
  вместе.
- Храните ключи внешних сервисов в защищённом окружении, например на
  сервере интеграции. В коде плагина, логах и фикстурах используйте безопасные
  значения. При появлении интеграции с языковой моделью храните системные
  промпты в одном тематическом модуле `prompts` с именами по назначению.
  Обработчики и сервисы получают текст промпта из этого модуля.

## Тесты и ревью

- Все тестовые данные, включая входы для одного сценария, ответы моков и
  ожидаемые данные, храните в `tests/fixtures/`. В тесте оставляйте шаги,
  вызовы и проверки. Ожидаемые данные контракта задавайте независимо от
  констант реализации. Общие данные и хелперы переиспользуйте между тестами.
- Для нового или изменённого поведения проходите Red → Green → Refactor.
  Для перестановки кода с сохранением поведения используйте существующие
  тесты и подходящие статические проверки.
- Перед сдачей изменений кода пройдите весь diff задачи, включая новые
  файлы, с [code-reviewer](../.agents/skills/code-reviewer/SKILL.md).
  Сверьте код со спецификацией, конституцией и этим гайдом. Проверьте
  константы и дубли, абстракции, деструктуризацию, JSX, ошибки, фикстуры,
  сохранение контрактов и рамок задачи. Результаты ревью реализации
  фиксируйте в `review.md` рабочей спецификации.
- После исправлений выполните затронутые проверки, `npm test` и
  `npm run build` (она включает TypeScript-проверку). Запишите реально
  выполненные команды и результаты в `verification.md`. Отразите оставшиеся
  замечания и статус проверок в Obsidian.
