# Конституция Project Flow Agent

## Основные принципы

### I. Markdown — источник данных

Постоянное состояние проектов и задач хранится в Markdown-файлах хранилища Obsidian.
Интерфейс получает состояние из файлов. Данные интерфейса, например состояние
раскрытия блока, принадлежат самому экрану.

### II. Ядро, интеграция с Obsidian и интерфейс

Ядро на TypeScript разбирает Markdown и применяет правила работы с задачами.
Оно принимает данные и возвращает результат и диагностику. Ядро должно
тестироваться без запуска Obsidian и React. Адаптер отвечает за чтение файлов,
события и открытие ссылок через API Obsidian. `ItemView` связывает адаптер, ядро
и React. Компоненты React получают данные и обработчики действий.

### III. Доступ к рабочему хранилищу

Первый пакет «Текущие задачи» читает рабочее хранилище пользователя.
Открытие и обновление вкладки сохраняют Markdown без изменений. Некорректные
поля получают диагностику, а распознанные задачи остаются доступны.
Каждая будущая операция записи требует отдельного согласования в спецификации
соответствующей фичи.

### IV. Проверяемая реализация

Изменения проверяемого поведения проходят цикл Red → Green → Refactor.
Разбор и пограничные случаи проверяются на примерах Markdown в репозитории.
Интеграцию с Obsidian проверяет агент, а пользователь принимает результат
на согласованных контрольных точках. Команды, результаты и ограничения
проверок фиксируются в `verification.md` согласно `AGENTS.md`.

## Стек разработки

В первом пакете React работает во вкладке Obsidian, Zod проверяет поля,
извлечённые из Markdown. Сборку выполняет esbuild. Режим `watch` и Hot Reload
используются для проверки новых сборок в рабочем Obsidian.

## Работа с Git

- Каждая новая фича из «Карты проекта» разрабатывается в отдельной новой ветке.
  В заголовке `spec.md` указывается название фичи, а в самой спеке — ветка,
  указанная пользователем, и соответствующий пункт карты. Перед изменениями
  агент сверяет текущую ветку с указанной.
- Spec Kit привязывает рабочую спеку к каталогу через `.specify/feature.json`.
  Ветку выбирает пользователь. Автоматическое создание веток и коммитов
  через Git-расширение, Git-хуки или скрипты Spec Kit запрещено.
- Локальный коммит допустим по явному поручению. Полное сообщение коммита
  дословно повторяет заголовок первого уровня рабочего `spec.md`, включая
  регистр и пунктуацию. Маркер Markdown `# ` в сообщение не входит.
- На удалённом репозитории агенту разрешены чтение и обычный push в указанную
  пользователем ветку. Push выполняется по явному поручению. Pull request
  создаёт пользователь.

## Управление изменениями

Изменения принципов согласуются с пользователем. При обновлении конституции
сверяются инструкции и шаблоны Spec Kit. Несовместимые изменения повышают
мажорную версию, новые принципы — минорную, уточнения — патч-версию.
Соответствие конституции проверяется в плане и при итоговой сверке со спекой.
